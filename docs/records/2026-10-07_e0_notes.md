# E0 紀錄（2026-10-07，分支 rebuild/e0）

設計書 v1.1 §0.2、§6、§11.1 的 E0a 與 E0b。

## E0a：退役 sparse／hybrid 臂

### 改了什麼

- 刪除 `backend/database/qdrant_hybrid.py`、`backend/utils/sparse_encoder.py`。
- `hybrid_retriever.retrieve_hybrid` 直接走 dense，呼叫 `qdrant_db.search_hybrid_dense`。
- `main.py` 不再初始化 sparse encoder；CKIP 不再載入。
- 刪除設定 `bm25_vocabulary_path`、`hybrid_prefetch_limit`、`hybrid_fusion_method`。
- 保留設定 `hybrid_search_enabled`、`qdrant_hybrid_collection`：前者決定查哪個 collection，也決定標籤。
- `docker-compose.yml` 拿掉 `./output/bm25_vocabulary.json` 的 bind mount。

### 為何行為逐位相同

1. **路徑選擇沒變。** prod 容器的 env 是 `HYBRID_SEARCH_ENABLED=true`，所以 `_get_semantic` 仍走 `retrieve_hybrid`。旗標名稱與預設值都沒動。
2. **舊路徑實際上只跑 dense。** 舊呼叫鏈如下：
   - sparse encoder 已初始化（詞表 20,587 個詞），CKIP 斷出詞表內的詞，於是進入 `hybrid_search`。
   - qdrant-client 1.8.2 沒有 `query_points`（backend venv 實測 `hasattr` 為 False；映像的 `uv.lock` 與 HEAD 相同），因此退回 `dense_only_search`。
   - 最後呼叫 `client.search(collection_name=qdrant_hybrid_collection, query_vector=("dense", v), limit=k)`。
   - 新路徑的呼叫逐參數相同。其餘參數（`with_payload`、`score_threshold`、`search_params`、`offset`）兩邊都沒傳，都用 client 的預設值。
3. **查詢向量沒變。** `embedder.encode_query` 在 E0a 沒動。
4. **hit 欄位對應沒變。** 仍是 `payload or {}`，`parent_pericope_id` 也照舊取出。
5. **candidate 組裝沒變。** 原碼搬進 `_candidate`：
   - 逐筆依序 await PG。
   - 權重：verse 0.70，其他 0.65。
   - 欄位名照舊是 `hybrid_score`。
   - `source_strategy` 為 `hybrid_hybrid`。
6. **標籤沒變。** fallback 路由的策略名仍是 `hybrid`。candidate 標籤 `hybrid_hybrid` 與 prod 日誌的 587/587 次「Hybrid retriever (hybrid)」一致。
7. **測試證據。** `backend/tests/test_hybrid_dense_arm.py` 先在舊碼上跑：用 monkeypatch 模擬 prod 的 sparse 狀態，並用只有 `search`、沒有 `query_points` 的 client，6/6 通過。換成新碼後同一份測試也是 6/6 通過。

### 唯一的差異：只影響標籤

- 舊碼在 CKIP 斷不出詞表內的詞時，標籤是 `hybrid_dense_only`。例如「誰？」「他是誰」「為什麼」。
- 新碼一律是 `hybrid_hybrid`。
- 兩種情況查的 Qdrant 呼叫相同，所以檢索結果相同。
- 這兩個標籤都不在任何排序表裡，包括 `strategy_order`、`_PINNABLE_GRAPH_STRATEGIES`、`strategy_priority` 與 book_anchor。因此不影響排序，只有 `found_by` 與 API 的 strategy 字串不同。
- 實測 GT 500 題中有 0 題落入這種情況（backend venv、CKIP、prod 詞表）。
- 舊碼在 CKIP 拋例外時會記成 `errors["hybrid"]`；新碼沒有這條失敗路徑。

### 回滾注意

- 若把映像換回 prod 9bc112a6，但 compose 沿用本分支（沒有詞表 mount），舊碼會找不到詞表，標籤因此變成 `hybrid_dense_only`；檢索結果相同。
- 要讓標籤也一致，回滾時要連同舊的 `docker-compose.yml` 一起換回。
- `docker-compose.staging.yml` 刻意不動：backend-staging 跑的是 `bible_rag-backend:latest`，而 mount 對新碼無害。

### 只為 sparse 存在的依賴（不改 pyproject／uv.lock）

- `backend/pyproject.toml` 的 `ckip-transformers>=0.3.0`。
- 它的相依套件（torch、transformers、tqdm）backend 本來就要用。
- 留待之後統一重鎖時移除（D-20）。

### 尚未退役（不在 E0a 範圍）

- `scripts/generate_sparse_vectors.py`、`scripts/sparse_encoding/`、`scripts/import_qdrant_hybrid.py`。
- 其中 `import_qdrant_hybrid.py` 產出的 `bible_embeddings_hybrid` 正是 backend 仍在查的 collection，R1 改用 `passages__{build_id}` 之前不能刪。

## prod 映像 9bc112a6 與本分支起點 2542102 的 backend 差異（G33）

比對方式：`docker run --rm --entrypoint sh bible_rag-backend:latest` 把 `/app/backend` 打包出來（不含 `.venv`、`__pycache__`、`.pytest_cache`），再與起點逐檔 `cmp`。

**內容不同的 5 個檔：**

| 檔案 | 差異（HEAD 相對映像） |
|---|---|
| `database/neo4j_db.py` | 新增 `_CURATED_XREF`；交叉引用排序改為 curated 優先，votes 預設改為 0，移除 999 哨兵（7cd33c4）；`labels()` 排序；`LIMIT` 前加 md5 決勝（087ab0d） |
| `database/postgres.py` | 實體與 mention 查詢的 `ORDER BY` 加 md5 決勝（087ab0d） |
| `utils/retrieval/cross_ref_retriever.py` | 改讀 `curated` 旗標並據此定權重，不再以 votes ≥ 999 判定 curated（7cd33c4） |
| `utils/retrieval/entity_path_retriever.py` | 兩個 `LIMIT` 前加 md5 決勝（087ab0d）；改一段 docstring |
| `utils/retrieval/router.py` | 只改兩段註解 |

**只在 HEAD 有的 5 個檔**：`probes/__init__.py`、`probes/xref_measure.py`、`tests/test_cross_ref_weight.py`、`tests/test_cypher_determinism.py`、`tests/test_xref_measure.py`。

**其餘檔案逐位相同**，包括 `pyproject.toml`、`uv.lock`、`config.py`、`main.py`、`embedder.py`、`reranker.py` 與 `hybrid_retriever.py`。

**影響。** 前 4 個檔的改動都在 Neo4j／實體／交叉引用路徑上，預設策略 `["event_registry"]` 走不到這些路徑。不過 `/api/v1/entity` 與 opt-in 策略的結果順序會不同。因此 E0a 的 G-IDENT 對照臂是 prod 映像；不通過時，要加跑「HEAD 但不含 E0a」的歸因臂。
